# ADR-005 — Search Architecture (Provider Abstraction)
Status: Accepted
Date: 2026-06-03

## Context

TalentFlow's search surfaces today rely on Postgres full-text and trigram
indexes. This works at small scale. At 100k+ candidates per tenant,
Postgres-only search becomes a bottleneck:

- Full-text queries compete with transactional writes for the same DB
- Faceted search (status × skills × location × experience) becomes slow
- Semantic / vector search is poorly supported without `pgvector` plus
  significant tuning
- Synonyms and tokenization are language-dependent and hard to maintain

We have not yet hit these limits. But the day we hit them, swapping the
search backend will touch dozens of services unless we abstract now.

The mandatory addition from the architecture review requires the
abstraction to ship in Phase 1, with two implementations: Postgres
(default) and OpenSearch (deferred but planned).

## Decision

### 1. SearchProvider interface

A single interface in `apps/api/src/modules/search/providers/search-provider.interface.ts`:

```
interface SearchProvider {
  name: 'postgres' | 'opensearch';

  search(req: SearchRequest): Promise<SearchResponse>;
  indexOne(doc: IndexDocument): Promise<void>;
  indexBulk(docs: IndexDocument[]): Promise<BulkResult>;
  delete(entity: EntityRef): Promise<void>;
  rebuild(entityType: EntityType, organizationId: string): Promise<RebuildJob>;
  capabilities(): SearchCapabilities;
}

interface SearchRequest {
  organizationId: string;          // mandatory; RLS-equivalent
  entityTypes: EntityType[];       // candidate | job | vendor | submission | resume
  query: string;                   // user input
  filters?: SearchFilter[];        // typed filter chips
  sort?: SearchSort;
  page: { offset: number; limit: number };
  facets?: string[];               // request facet aggregations
}

interface SearchResponse {
  hits: SearchHit[];
  total: number;
  facets?: Record<string, FacetBucket[]>;
  tookMs: number;
  provider: 'postgres' | 'opensearch';
}

interface SearchCapabilities {
  semanticSearch: boolean;         // vector / embedding-based
  fuzzy: boolean;
  highlighting: boolean;
  facets: boolean;
  multiTenant: 'shared-index' | 'index-per-tenant';
}
```

The interface exposes `capabilities()` so callers can degrade gracefully
when a feature isn't available (e.g., the dashboard tries semantic search,
provider returns `semanticSearch: false`, the call falls back to keyword).

### 2. Application surface is provider-agnostic

The `SearchService` injects a `SearchProvider` token. Callers never know
which provider they're hitting. Switching providers is a configuration
change, not a code change.

```
@Injectable()
export class SearchService {
  constructor(@Inject(SEARCH_PROVIDER) private provider: SearchProvider) {}

  async candidates(orgId: string, q: string, filters?: SearchFilter[]) {
    return this.provider.search({
      organizationId: orgId,
      entityTypes: ['candidate'],
      query: q,
      filters,
      page: { offset: 0, limit: 30 },
    });
  }
}
```

### 3. PostgresSearchProvider (default, ships Phase 1)

- Uses `tsvector` columns with GIN indexes for full-text
- Uses `pg_trgm` for fuzzy matching
- Filters compile to SQL WHERE clauses
- Facets compile to GROUP BY aggregations
- No semantic search (returns `capabilities().semanticSearch = false`)
- RLS enforces tenant scoping (ADR-002)

This is the same behavior the app has today, repackaged behind the
interface.

### 4. OpenSearchProvider (planned, ships Phase 6 or Phase 7)

- Each tenant has documents tagged with `organizationId`
- Index strategy: one shared index per entity type
  (`candidates`, `jobs`, etc.) with `organizationId` filter on every
  query. Cheap to operate at our expected scale (< 10M docs/index)
- Tenant isolation enforced application-side; the provider rejects any
  request without `organizationId`
- Supports semantic search via the `hybrid` query (BM25 + k-NN over an
  embedding field). Embeddings generated by the AI service (ADR-004) and
  indexed at write time
- Built-in fuzzy + highlighting + faceting

When OpenSearch ships, swapping is a single line of configuration:

```
@Module({
  providers: [
    { provide: SEARCH_PROVIDER, useClass: OpenSearchProvider }
  ]
})
```

### 5. Indexing pipeline (consumes events from ADR-003)

A `search-indexer` event consumer subscribes to:

- `candidate.created`, `candidate.updated`, `candidate.deleted`
- `job.created`, `job.updated`, `job.deleted`
- `submission.created`, `submission.updated`
- `vendor.*`
- `resume.parsed` (for full-text content)

For each event:

1. Load the canonical record (single Prisma query)
2. Build the `IndexDocument`
3. Call `provider.indexOne(doc)`

With Postgres provider, this is a no-op since data is already in Postgres
(the document IS the row). With OpenSearch, this writes to the index.

This indirection lets us run **both** providers in parallel during
migration: write to both; serve from Postgres; verify OpenSearch matches;
flip read traffic.

### 6. Index rebuilds

A `rebuild` operation triggers a full reindex for one entity type, one
tenant. Backfills new tenants or recovers from index corruption. Runs as
a BullMQ job at low priority.

### 7. RLS interaction

The Postgres provider relies on RLS — the session GUC is set before the
search SQL runs, so policies apply.

The OpenSearch provider is application-scoped. Every query must include
`{ term: { organizationId: <uuid> } }`. The `SearchProvider` interface
enforces this by requiring `organizationId` on `SearchRequest`. Any code
path that constructs a `SearchRequest` without `organizationId` fails type
checking.

### 8. Future capability: semantic search

When OpenSearch ships:

- Candidate documents include an `embedding` field generated by the AI
  service from a canonical "candidate summary text" (skills + title +
  recent jobs). Re-embedded on resume update.
- Job documents include an `embedding` field from job description.
- Queries can be (a) pure keyword, (b) pure semantic, or (c) hybrid.
- The UI feature "AI Match" graduates from per-pair computation to
  candidate-against-all-jobs at query time.

This is **opt-in per tenant** (ADR-004 §9). Tenants who have disabled AI
get the keyword-only path automatically.

## Consequences

### Positive

- Production app ships on the simpler stack; no premature OpenSearch
  operational cost
- Swap is a config change, not a code change
- Provider differences (capabilities) surfaced to callers cleanly
- Indexer is the same code regardless of provider
- Migrations can run both providers in parallel for verification

### Negative

- Abstraction overhead: building `SearchRequest` and reading
  `SearchResponse` is more code than direct SQL
- Postgres provider can't perfectly emulate OpenSearch's full feature set
  (no semantic search, weaker faceting). Capabilities surface keeps this
  honest.
- Index drift between Postgres and OpenSearch during a migration must be
  reconciled.

## Alternatives considered

**Just use Postgres forever** — rejected. Scaling ceiling well below 1M
candidates per tenant for faceted search.

**Postgres + pgvector for semantic, no abstraction** — rejected. Still
locks us to Postgres operationally; faceted-search ceiling unchanged.

**Algolia / Typesense (managed)** — rejected. Pricing is per-record per
month; at 1M candidates × 100 tenants this is prohibitive.

**ElasticSearch** — viable; we chose OpenSearch for the AWS-native managed
option and the Apache 2.0 license stability. Codebase-compatible enough
that switching is feasible.
